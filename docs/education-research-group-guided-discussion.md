# 引导式研讨：第一批实现与用户测试

日期：2026-11-16。起点 `main`／`65810d2`，干净工作区，本地记录 ahead 76，未 fetch／push。用户授权保留导师、A、B、资料员，由用户作为课题发起人和最终决策者参与。仅代码逻辑、隔离存储、类型、lint、架构、格式和构建由开发者验证，界面与真实模型由用户测试。

## 使用方式

融合课题面板新增“与团队研讨”。可以创建议题或点击历史议题的“继续这个议题”，输入自由回答、反问、尚不确定的想法，或请团队调查后再回答。默认是“探讨想法／自由回答”；明确选择“正式指令”才按指令送给导师。用户原话、身份、意图、输入版本、导师解释和每轮问题分别保留。

导师在实际运行中可主动提出关键问题，面板标题显示待答提示。导师先看历史、自己查清可查事实，只问影响下一步的未知。其他成员保留独立工作及互评，通过原消息通道向导师提供建议，由导师统一组织向用户的讨论。没有新增角色或模型执行循环。

每轮导师说明理解、理由或落实安排，可附一个开放问题；收到回答后才能继续这一议题的下一轮提问。不必选择固定答案。无需再问时导师以空问题收束，显示“本轮已收束”；这只是研讨收束，不代表指令已落实、稿件接受或用户批准。

当前只接入已有融合课题；旧两／七阶段、CYZ 及其历史不迁移。暂停或已完成课题须先用原控制恢复当前任务再发送，不能绕过原状态或预算限制；未创建课题时不提供独立的会前访谈。研究过程中实际需要的权限仍经原“需要我处理”决定入口，研讨不能代选。

## 代码边界与存储

- 记录位于原课题 `m3.discussions`，按议题和输入 revision 分组，消息只追加。用户／导师身份由宿主赋值，模型不能自报用户指令。历史输入版本不能用新回答改写。
- 用户发言与导师 member input 在同一个协调器持久化事务中登记，保存成功后才经原准入与 follow-up 机制送达；占用原有执行名额并计入原账本。正在执行时排队，存储失败不保留半条发言或启动替代请求。
- 用户消息有固定 ID；网络或界面答复未知时重试同一条不会重复登记或派发。并发新消息使用 expectedMessages 拒绝过期提交，界面保留原文字供核对，不能覆盖其他轮次。
- 模型仅导师本人、在当前有效执行中可以 `discussion-post`，记录原 tool call ID；重复调用幂等。每个版本最多一个等待用户的问题；同议题导师不能在用户未回答时连续追问；完全相同的问题不能换议题再次提出。
- 自由探讨仅作为导师的会话接续，不创建 decision、材料采用或正文修改。具备同 ID 用户原始研讨记录的 idea 不进入“用户要求改稿”的接受门禁；正式 instruction 仍受既有 member input 处理门禁约束，研讨摘要不能代替实际交付或具名改稿说明。
- 导师发起问题本身不创建任务许可依赖或全组暂停。确实缺少权限时仍使用 request-decision，仅阻塞相关任务。研究事实、方法及内容门禁不因“老板指令”跳过。
- 只在导师 status 中提供完整研讨记录，不向 A/B 初判上下文自动广播。需要落实的任务沿用现有成员沟通与版本变更流程，不能靠研讨记录冒充实际修改。
- 研讨结构在保存／重载时校验：版本、身份、长度、消息 ID、轮次及待答数量。原子存储、备份只读保护和失败证据策略保持不变。

## 本批限制

相同议题／消息身份、完全相同问题、一次一个待答问题由程序限制；换措辞的语义重复、追问是否有价值、是否恰当收束仍依赖模型遵守指导，必须真实测试，不能称已解决所有重复打扰。

“一个问题”是一个文本字段，提示要求只问一个关键问题，程序不会证明其中没有多个问号或暗含多个问题。没有新增系统通知、桌面弹窗或催答计时器。已有连续用户补充可以排队，导师仍需实际运行才能回应。

“正式指令”送达导师，不会无条件改问题、换路径或自动采用材料；这些变更仍走原有版本／许可流程。普通聊天里输入的文字继续走原成员输入机制，只有此研讨入口明确标记的探讨享有相应语义区分。真实模型能否严格把设想与执行分开，需要用户评估。

## 验证计划与结果

成功条件：自由回答能持久保存并进入原导师接续；原四会话和稿件不变；探索不自动变许可，指令仍要求处理；未答不重复追问；重试幂等；过期版本／越权请求拒绝；存储失败不派发且保留原字节。

5. 等待回答期间让其他成员继续研究；检查不发生多成员轮番催答。另一个需要正式许可的条件仍从原决定入口处理。
