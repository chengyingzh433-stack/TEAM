## 第一批：可编辑 Word 与同版本交付

对应 FR13、AC17、AC31。成功条件：从同一不可变稿件／项目快照产生 DOCX、Markdown、HTML 和溯源；DOCX 的文本、标题、表格为 OOXML 可编辑结构；来源可读且内部编号移入附录；审阅稿不改变接受状态；任何文件或状态保存失败不能登记成功，旧稿和失败产物保留。

实现：

- `paper-docx.ts` 在 main 端使用现有 fflate 生成无外部资源的 OOXML；没有增加系统 Word、Python、网络或模型依赖。A4、中文宋体／标题黑体、六级标题、书签与可点击静态目录、原生表格及重复表头。目录为导出时的标题快照，编辑后不会自动刷新页码。
- 正文的 `[SRC:...]` 转为作者年份引用；缺来源显式标为待核验。`[ANALYSIS:...]` 转为可读计算序号；内部 ID、来源详情与计算对应留附录。Markdown 保持原稿字节（加结尾换行），可与溯源稿件 SHA 核对。
- 在首次文件 I/O 前复制项目与稿件。DOCX 文件 SHA、原稿 SHA、输入版本、稿件 ID、交付状态以及现有材料／结果／审阅记录写入同包溯源。不重新取最新稿。
- 原本轮接受路径仍由现有协调器接受门禁触发；增加 DOCX 入口。新增审阅导出 action 只接收本课题稿件 ID；当前稿件的审阅导出通过同一持久化队列保存，不改接受状态，不派发模型。审阅交付保留历史及版本标签。
- 每次导出使用独立目录、文件排他创建，全部文件写完后才返回交付记录。重复导出保留旧包；失败目录不删除，后续尝试不会被原先部分文件阻挡。旧项目没有 DOCX 时不伪造 Word 入口。

验证计划与范围：Node 单元检查实际临时文件、ZIP/XML、数值表格、标题／目录关系、中文字体声明、来源映射、并发新稿快照、失败原文件保护、旧记录兼容及协调器保存后重载；再串行执行 `NODE_OPTIONS=--max-old-space-size=6144 pnpm check` 和 `pnpm --filter @lancer/desktop build`。不启动 Electron、Word/WPS、真实提供商或常用安装。

失败记录：`.artifacts/m4-docx-unit-first-20261114.log` 中夹具项目 ID 无效；second 批进一步暴露夹具缺四成员及成果 UUID，均修正夹具而不放宽产品校验。两批日志和 trace 保留。最终 `pnpm check` exit 0，desktop 918 passed／1 个既有 skip、新增 M4 5/5；桌面 build exit 0。代码提交 `f4f4388`，日志与结果见开发进度末尾。

## 用户功能测试：待执行

1. 在有 A 稿的课题点击“导出当前审阅稿（待核验）”，打开审阅交付的 Word、HTML、Markdown 与溯源；确认课题仍保持原状态，未自动接受或启动成员。
2. 新稿完成原有全文终审后打开“可编辑 Word”，核对“本轮接受稿”及输入版本、稿件 ID。既有历史接受包不会自动补写 Word；本批没有历史包升级操作。
3. 在 Word/WPS 中修改正文和表格单元格；检查中文、六级标题导航、静态目录跳转、长表重复表头与跨页布局。字体可用性、分页、渲染和实际打开均尚未由开发者验证。
4. 对照原稿核查数字、否定、引用作者年份以及附录对应。当前转换范围是 Markdown 标题、管道表格、普通段落和围栏文本；复杂 Markdown 行内语法保留文字，图片、数学公式排版及期刊样式不在本批实现范围。
5. 导出期间产生新稿，核对旧包保持固定版本、新稿仍需相应审阅；旧审阅包只作为历史记录，不冒充当前接受稿。
